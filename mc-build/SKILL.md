# Minecraft 建造执行（落地阶段）

本技能负责 Minecraft 建筑流水线中的建造执行阶段，其职责是将蓝图写入游戏世界并完成逐格验收。新建筑的设计工作由 mc-design 技能承担；对已建成建筑的微调工作由 mc-modify 技能承担，仅当用户明确要求重建或重新设计时，才回到本技能执行整体落地。

## 通用约定

以下约定是本技能执行时必须遵守的基础规则（设计阶段的对应约定见 mc-design 技能，彼此独立）。

1. 引擎目录在下文中以 `<ENGINE>` 表示，其取值来自环境变量 `MC_BUILD_HOME`，默认值为 `D:/mcserver`。执行 Node 脚本时统一使用 `C:/Users/ASUS/.workbuddy/binaries/node/versions/22.22.2-2/node.exe`。
2. 蓝图的唯一真相源是 `<ENGINE>/schematics/<名字>.json` 文件；`.litematic` 文件作为存档使用；`<名字>_fills.txt` 文件作为表演模式的输入使用。
3. 执行任何建造操作之前，单人世界必须已经对局域网开放并记录端口号，且世界已开启作弊。
4. 五十格阈值：当操作涉及的方块数量少于 50 格时，优先采用内联方式而不创建文件；当数量达到或超过 50 格时，改用蓝图文件通道。
5. 验收标准：verify-region 检查结果中的缺失、不符、未加载三项必须全部为零；「多余」不作报错，仅作为普通警告参考（建造一般只会少不会多，多余多由基座台面、天然地形等蓝图外衬底造成，判据价值低）；观感层面的最终审定通过用户 F2 截图完成，读图方法见 mc-screenshot 技能。
6. 三条物理规则必须遵守：树叶必须携带 `[persistent=true]` 状态，否则会自然凋零；灯笼不能放置在半砖之上，否则没有完整支撑面；藤蔓不能依附于玻璃板，即使强制放置也会被方块更新弹掉。
7. 深度参考资料位于本技能的 references 目录，本文件正文不重复其内容；全部可执行命令集中列于本文件末尾的「命令速查」一节，正文只描述流程与决策逻辑。

## 工作流程

**第 0 步：确定输入。** 本步骤的目的是确认本次建造采用哪种输入形式，三种形式互斥。第一种是内联直建，仅适用于特别简单的情形：建筑必须是能够一眼写出的基本几何体（例如矩形平台、立柱、简单箱体），同时规模小于 50 格且无需复用；此时体素清单不落盘，直接作为 build-blueprint 工具的 blocks 参数传入，一次调用即完成建造。任何超出基本几何体范畴的建筑，都必须先经 mc-design 技能的设计器网页产出蓝图，禁止凭空猜测坐标并手写体素清单——手写坐标无法在落地前自查，错误只有建造之后才会暴露。第二种是引擎库蓝图，适用于 `<名字>.json` 已经位于引擎库的常规情形；若仅有 `.litematic` 文件，须先执行格式转换。第三种是外部复刻，适用于复刻外部获得的 `.schem` 或 `.litematic` 文件：先将文件复制入库并转换为 JSON，然后核对方块总数与元数据是否一致，最后在落地前扫描调色板确认其中不含游戏版本不认识的新版本方块；若含有，必须先生成替换补丁，避免整栋建筑反复重跑后被整条拒绝。

**第 1 步：探测地面并确定建造原点。** 本步骤的目的是保证蓝图落点与用户预期一致。使用 MCP 工具 get-block-info 检查目标点脚下一至两格的方块，因为游戏中 F3 界面显示的纵坐标是脚部所在格，脚下方块的实际高度会因站立方块或跳跃而在更低的一至三格之间变化；对目标区域四角各探测一次，以确认地面平整。同时在建造前确认目标区域内没有玩家或 bot 站立——站在目标格上会导致放置失败，或者方块被站位者撸掉（实测发生过 6 格方块被撸掉的事故），有站位者时先请用户离开或把 bot 挪开。

蓝图自身的坐标范围不一定从零开始，这一点在确定 originY 时必须先查明。图片还原类蓝图由抠图掩码生成，最低一行常常落在纵坐标大于零处，而 build-blueprint 的 originY 对应的是蓝图坐标 y=0 而不是最低一行，直接按地面高度传 originY 会让成品整体悬空若干格。正确做法是先取出方块的最小纵坐标，再用「期望的底层世界高度减去该最小纵坐标」反推 originY。建筑类蓝图通常从 y=0 起算，不受此影响。

**没有平坦地面时自建基座。** 若目标点附近找不到能容纳建筑占地（建议每侧再留约 2 格余量）的平地——例如虚空场景、窄平台、地面高低不平——可自行铺设基座/展台，无需询问用户：基座顶面与视线主参考面（周围地面/平台顶面）平齐，厚 2–3 格；整块基座超过 50 格时生成临时蓝图文件（如 launchpad.json）走秒落，建完删除文件；材质优先与周围地面相同，便于连成一体。注意：基座顶面在建筑底层之外露出的格子，会在验收时被判为「多余」，属预期衬底，按警告忽略（见第 3 步），不要拆除。

**第 2 步：选择落地模式。** 默认采用秒落模式，即通过 MCP 工具 build-blueprint 写入蓝图文件，这是常规情形。落地耗时与方块数近似成正比，比例系数取决于 `/fill` 压缩率：平涂像素图的色块连通性好，约每千格八秒；照片转出的杂色像素墙压缩率低，约每千格二十八秒。单次调用的指令数应控制在四千条以内，超出时按横坐标切成若干段逐段落地。当用户希望观看建造过程时，改用表演模式，即通过 perf_build.js 脚本驱动工人机器人走位、转向、挥手并逐条回放指令，其耗时约为秒落模式的十倍以上。表演模式脚本由 Agent 自己用后台命令执行即可（长任务用 run_in_background），不需要用户开终端——工人使用 XiaoGold 用户名，与 MCP 会话的 XiaoBuddy 是两个不同用户，不存在顶掉或连接冲突；唯一禁止的是用 XiaoBuddy 名字去跑表演脚本。

**第 3 步：验收。** 本步骤的目的是确认蓝图已完整、正确地写入世界。执行 MCP 工具 verify-region 时默认传 checkExtra=false，跳过「多余」检查——按经验建造只会少不会多，「多余」多由基座台面、天然地形等蓝图外衬底造成，判据价值低。缺失、不符、未加载三项必须全部为零；若出现缺失，按类别处理：依附类方块（藤蔓、灯笼等）先检查物理规则与指令顺序，再逐根补放；树叶缺失意味着自然凋零，补放时必须携带 `[persistent=true]` 状态，并将蓝图同步修改为带状态版本；蛋糕等可被消耗的方块缺失时，先询问用户，因为可能确实被吃掉了。若确有需要检查多余（例如怀疑误放），可开启 checkExtra 并当作普通警告看待，但不要因多余拆除任何方块，除非用户明确要求。随后请用户按 F2 截图进行观感终审，读图方法见 mc-screenshot 技能。验收通过后若还需修改，转入 mc-modify 技能执行差量微调，不做整体重建。

## 命令速查

以下命令按照工作流程的出现顺序排列，供执行时直接查阅。

```
# 第 0 步：将 litematic 转换为 JSON
node <skill>/scripts/convert_litematic.mjs <ENGINE>/schematics/<名字>.litematic <ENGINE>/schematics/<名字>.json

# 第 2 步：秒落模式（MCP 工具 build-blueprint）
# 参数：file=<名字>.json、originX/Y/Z；delayMs 默认 20 毫秒，数千条指令无事故。
#   5 毫秒基本可用，但出现过一次不可复现的指令丢失——由 verify-region 兜底抓取后单格补回即可。
#   九千条以上的大型建造应将 delayMs 放宽到 45 毫秒，因为 20 毫秒可能使机器人掉线；
#   /fill 指令具有幂等性，掉线后可直接重跑。
# 内联直建：将 blocks=[{x,y,z,block:"minecraft:…"},…] 数组直接传给 build-blueprint，同样传入 originX/Y/Z。

# 第 2 步：表演模式
# 前置：蓝图只有 JSON 没有 fills 时，先用官方转换器生成（不要手搓指令清单）：
node <skill>/scripts/json_to_fills.mjs <ENGINE>/schematics/<名字>.json [输出路径] [originX originY originZ]
# 回放：Agent 自己用后台方式运行即可（长任务用 run_in_background），不需要用户开终端；
# 工人用户名必须是 XiaoGold（与 XiaoBuddy 不同用户，不冲突）；用 XiaoBuddy 跑表演脚本才会顶掉 MCP 会话的 bot。
node <skill>/scripts/perf_build.js <端口> XiaoGold <ENGINE>/schematics/<名字>_fills.txt 400
# 末位参数为节拍（毫秒/条），默认 400；中断后可直接重跑，因为指令具有幂等性；如需慢镜头可调大该值。

# 第 3 步：验收（MCP 工具 verify-region）
# 参数：file=<名字>.json、originX/Y/Z、checkExtra=false（默认关闭多余检查）
# 缺失、不符、未加载三项全部为零方可通过；「多余」不作报错（多由基座台面/天然地形等衬底造成）
# 单格补放示例：
/setblock x y z minecraft:oak_leaves[persistent=true]
```

## 异常速查

以下各条描述常见异常的现象、原因与处理方法，更详细的背景见 references/pipeline.md。

- 当蓝图解析结果为零个方块时，原因通常是 litematic 新旧调色板格式的兼容问题，应检查引擎中的 parseLitematic 函数；格式规范记载于 mc-design 技能的 references/design.md。
- 当报错为 `ERR_UNSUPPORTED_ESM_URL_SCHEME`（提示 'c:' 协议）时，原因是 Windows 下的 ESM 不接受盘符开头的裸路径作为导入地址，处理方法是动态导入时一律使用 `pathToFileURL(绝对路径).href`。
- 当 build-blueprint 报告找不到蓝图时，原因是 JSON 文件尚未复制入引擎库，应先将其复制到 `<ENGINE>/schematics/` 再执行建造。
- 当修改引擎源码后行为未变化时，这是正常现象，因为运行中的 MCP 进程仍持有旧代码，需要开启新会话才会生效；过渡期间可使用 convert_litematic.mjs 桥接。
- 当无法连接游戏时，原因通常是局域网端口发生变化，应同步修改 mcp.json 并重新信任连接器。
- 当外部蓝图含有 1.21.4 及以上版本的方块（pale_oak、resin、creaking 等）而游戏为 1.21.1 时，包含未知方块的单条 /fill 指令会被整条拒绝，其症状是验收结果中「缺失」恰好等于这些方块类型的总数且「不符」为零；处理方法是在落地前扫描调色板，命中后生成同位置的替换补丁蓝图（例如将 pale oak 替换为 birch），而不是反复重跑整栋建筑。
- 当 verify-region 报告「多余」但「缺失」「不符」「未加载」均为零时：属正常衬底噪音，不作报错——多余来自严格包围盒扫描：蓝图某轴边沿格未铺方块时（圆形/异形底面、仅占最外一圈的装饰），基座台面、原有草地等世界方块会被判为多余。处理：默认 checkExtra=false 直接跳过；确需检查时按普通警告看待，不要因多余拆除任何方块。额外经验是设计期尽量让蓝图占满外延以缩小此边界现象（例如基座铺满方块而非空一圈仅放灯笼）。
