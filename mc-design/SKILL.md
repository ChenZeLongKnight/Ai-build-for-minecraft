# Minecraft 蓝图设计（设计阶段）

本技能负责 Minecraft 建筑流水线中的设计阶段，其职责是将设计构思转化为标准化的蓝图文件。本技能只管设计：设计过程在浏览器内的体素设计器中完成，不需要游戏世界处于运行状态；设计产物写入引擎目录，供后续流程取用，后续流程如何消费这些文件不属于本技能的知识范围。

## 网页设计器使用说明书（设计前必读）

**禁止绕过设计器**：一切设计必须且只能通过设计器网页完成。凭空猜测坐标并手写体素清单不是可选方法——手写的坐标无法在设计阶段自查，错误只有到游戏中才会暴露，且没有视觉反馈可供迭代。

**前置依赖（先确认再动手）**：操控设计器必须使用浏览器自动化 MCP 工具（如 browser-use / agent-browser / playwright 等，以下称「浏览器工具」）——它是本技能的第二条腿，没有它整个设计流程无法执行。开始设计前先确认该 MCP 已连接、其导航、JS 求值与截图工具可用；若不可用，先启用浏览器连接器再进入设计，不要退回手写体素。后文所说的「打开页面」「调用 vd 接口」「截图」，全部指通过该浏览器工具执行。

**打开方式**：用浏览器工具导航到 `file:///<skill路径>/assets/voxel_designer.html#ai`（URL 末尾的 `#ai` 片段会使页面打开时自动运行全链自测，用于确认接口可用；`#sample` 片段则自动载入水井示例）。页面依赖库位于同目录的 libs 文件夹，file 协议打开无任何网络依赖。

**调用方式**：打开和操控浏览器请使用 browser-use MCP 服务，通过其 JavaScript 求值功能直接调用页面提供的 `window.vd` 接口，不要模拟鼠标操作。所有方法同步返回 JSON，并镜像到页面右下角的 #aiOut 面板（截图亦可读出返回值）。

**接口全表**：

| 方法 | 说明 |
|---|---|
| `help()` | 输出接口总览 |
| `blocks()` | 输出 42 种可用方块 `[{id,label,mc}]`（含半砖、楼梯、栅栏、墙、灯笼、盆栽、营火、书架等造型方块） |
| `select(id)` | 选择默认方块，minecraft: 前缀亦可识别 |
| `place(x,y,z,id?)` / `erase(x,y,z)` | 单格放置与擦除 |
| `box(x1,y1,z1,x2,y2,z2, id\|null)` | 长方体填充；参数为 null 或 "air" 时清空该区域 |
| `build([[x,y,z,"stone_bricks"],…])` | 批量摆放，一次撤销批次加一次重建，是效率核心（上限 20 万格） |
| `voxels()` | 列出全部已放置的方块 |
| `state()` | 输出方块数、尺寸、各方块计数、工具、切片、相机与撤销深度 |
| `undo()` / `clear()` / `load(json)` | 撤销、清空与导入（接口层均不弹出确认框） |
| `export()` | 导出蓝图，返回 `{blueprint:{width,height,length,blocks:[{x,y,z,block}]}}` |
| `view('iso'\|'front'\|'back'\|'left'\|'right'\|'top'\|'fit')` | 相机预设 |
| `orbit(yawDeg,pitchDeg,dist?,tx?,ty?,tz?)` | 精确环绕相机 |
| `slice(true, y)` | 仅显示纵坐标不超过 y 的切片，用于检查内部结构 |
| `screenshot()` | 输出画布的 PNG dataURL（通常直接使用浏览器截图工具更方便） |
| `sample()` | 载入示例建筑水井 |

**两条容易误读的行为（实测有模型在此浪费排查轮次，务必先读）**：

- build 的同格覆盖语义：批量摆放时若多个条目落在同一坐标，后放的方块会覆盖先放的（与游戏内 /setblock 的覆盖写语义一致）。返回值中的 overwritten 字段报告本批次内被覆盖的放置次数；overwritten 大于 0 通常意味着体素清单存在坐标重叠，应回头检查生成逻辑，而不是继续叠加摆放。
- export 的坐标归一化：导出的蓝图坐标会将三轴各自平移到从 0 开始（每轴减去该轴最小值），原始最小角记录在返回值与蓝图的 origin_min 字段中。因此导出结果的坐标与摆放时的输入坐标不一定相同，这不是错误；蓝图坐标本来就是相对原点的，落地定位由后续流程的 origin 参数负责，无需把 origin_min 加回蓝图。

**设计器的三条已知限制**：

- 网页设计器放置方块时不携带状态信息：半砖默认为下半（type=bottom），楼梯默认朝北（facing=north），栅栏与墙在游戏内会自动连接故无影响。当设计需要定向楼梯、上半砖、悬挂灯笼等自定义状态时，应改走脚本路线，在设计模板复制品中直接书写如 `minecraft:spruce_stairs[facing=south]` 的完整状态名称；litematic 写入器与 /fill 指令均会原样携带状态，此路径已实测可用。
- 设计器输出的树叶自动携带 `[persistent=true]` 状态（普通树叶附近无原木会自然凋零，此为设计器内置的修复）。
- 设计器的调色板即能力边界：build 接口会跳过调色板之外的方块并在返回值中报告 skippedUnknown，因此设计前应先调用 blocks 接口核对可用方块。若缺少所需方块，可向设计器的 BLOCKS 注册表中补充（采用程序化像素纹理；注意技能资产与工作区副本两处文件均需修改）。

**物理规则（设计体素时必须遵守）**：

- 围水的墙体必须使用全方块（圆石、石砖等）；墙、栅栏、台阶会漏水。
- 依附类方块必须有支撑：藤蔓依附于其 west=true 等属性所指向一方块的完整面；灯笼悬挂时上方须有方块、落地时下方须有方块；地毯、床、门必须贴地放置。
- 藤蔓不能依附于玻璃板，因为玻璃板不构成完整面；即使通过 /setblock 强制放置，也会随方块更新被弹掉。若希望藤蔓攀爬玻璃窗，应将该格玻璃板换成玻璃块，或放弃该藤蔓。
- 悬空的沙子、混凝土粉末、沙砾会塌落；火把必须贴面放置。
- 指令顺序会影响物理结果：依赖方块的支撑块必须先落地。落地工具按纵坐标自低向高执行，天然安全，但同一层内仍会有藤蔓类方块漏网，由后续流程验收后逐根补放。

**推荐的设计节奏**：清空画布，批量摆放主体，切换到适配视角配合浏览器截图检查整体，再以环绕相机与切片检查细节，修改后复查，核对状态后交付。坐标系中 y=0 表示地面。

**交付原则（数据不过模型，重要）**：设计完成即调用 `vd.download()`，由浏览器把蓝图落成磁盘文件，随后用文件操作移动改名到引擎目录。落盘位置固定：blueprint.json 始终保存在当前工作区的 `.playwright-mcp/` 目录下（实测确认），因此移动命令直接写 `.playwright-mcp/blueprint.json` → `<ENGINE>/schematics/<名字>.json`，不需要任何查找或全盘搜索。无论蓝图大小，一律走下载通道；禁止调用 `vd.export()` 后把返回值 JSON 抄写或注入到模型上下文中再写文件——大蓝图会在上下文中进出一次，既浪费又可能抄写走样。文件落位后不再回读核对内容：设计好了就是设计好了，设计阶段到此结束，正确性由后续流程的验收兜底。`vd.export()` 仅在需要查看方块数量等元信息时使用，不作为交付通道。

## 设计约定

1. 引擎目录在下文中以 `<ENGINE>` 表示，其取值来自环境变量 `MC_BUILD_HOME`，默认值为 `D:/mcserver`，是设计产物的写入目标。执行 Node 脚本时统一使用 `C:/Users/ASUS/.workbuddy/binaries/node/versions/22.22.2-2/node.exe`。
2. 设计产物为三个文件，统一以 `<名字>` 为前缀，全部写入 `<ENGINE>/schematics/`：`<名字>.json` 是蓝图主文件（必需），内容为 `{width,height,length,blocks:[{x,y,z,block}]}`，坐标相对蓝图原点；`<名字>.litematic` 是存档文件（推荐），Litematica 模组可直接打开；`<名字>_fills.txt` 是 /fill 指令清单（按需生成），每行一条指令。
3. 深度参考资料位于本技能的 references 目录（脚本路线细节与蓝图格式规范），本文件正文不重复其内容；全部可执行命令集中列于本文件末尾的「命令速查」一节，正文只描述流程与决策逻辑。

## 工作流程

**第 1 步：路线选择。** 本步骤的目的是根据建筑特征选择设计工具。路线 A 为网页设计器，是绝大多数情形下的唯一方法，适用于一切需要构思、试摆或查看效果的建筑；使用方法见上文使用说明书，执行前提是浏览器自动化 MCP 已连接。路线 B 为脚本设计，仅在结构具有明显程序化特征（严格对称、循环重复单元、参数化曲线）且手工摆放不便时使用；该路线通过复制设计模板并修改其中的 buildDesign 函数实现，产物会直接写入引擎库，不依赖浏览器工具。除此之外不存在第三条路线。

**第 2 步：设计与自查。** 本步骤的目的是产出并校验体素模型，按使用说明书中的推荐节奏执行：先清空画布，再批量摆放主体；然后检查整体与细节，修改后复查，直至满意；最后核对方块数量与整体尺寸。

**视觉自查原则（重要）**：当对坐标推算的返回结果感到困惑时，不要继续在文字与数字层面反复推理，而应立即调用浏览器截图能力，以多模态方式直接查看设计器中建筑的实际样子——看一眼渲染结果远比心算坐标可靠。截图落盘位置固定：当前工作区的 `.playwright-mcp/` 目录，文件名形如 `page-<时间戳>.png`（实测确认），用工具返回的相对路径直接读图即可，不需要任何查找或全盘搜索。判断标准是「大差不差」：只要建筑的形状、比例、朝向与设计意图大体相符，即可判定通过，无需逐格核对坐标；发现明显偏差时，回到设计器修改后再次截图确认。本技能的截图通道（浏览器对设计器渲染画面）与 mc-screenshot 的 F2 截图通道（游戏内画面）是两条独立通路，互不通用。

**第 3 步：交付产物。** 本步骤的目的是产出标准化的设计文件，按上文「交付原则」执行，蓝图数据不经过模型上下文。三个文件统一以 `<名字>` 为前缀写入 `<ENGINE>/schematics/`。`<名字>.json` 必须生成：路线 A 调用 `vd.download()` 把 blueprint.json 下载到本地（浏览器下载目录），再用文件操作移动并改名为 `<ENGINE>/schematics/<名字>.json`；路线 B 自动产出。`<名字>.litematic` 推荐生成，使用 write_litematic.mjs 脚本从 JSON 转换得到。`<名字>_fills.txt` 仅在收到指令清单需求时生成，其压缩规则为按纵坐标自低向高排序、同种方块的连续区段合并为一条指令。交付完成后不回读 JSON 核对，直接结束设计阶段。

## 命令速查

以下命令按照工作流程的出现顺序排列，供执行时直接查阅。

```
# 第 1 至 2 步，路线 A：打开网页设计器
# 打开和操控浏览器请使用 browser-use MCP 服务
file:///<skill路径>/assets/voxel_designer.html#ai

# 路线 A 的接口调用序列（通过浏览器自动化的 JS 求值执行，详见上文说明书）：
#   vd.clear() 清空画布；vd.build([[x,y,z,"stone_bricks"],…]) 批量摆放
#   vd.view('fit') 相机预设；vd.orbit(yaw,pitch,dist,目标) 环绕相机；vd.slice(true,y) 切片
#   vd.state() 核对数量尺寸；vd.help() 查询接口；vd.blocks() 查看可用方块
#   对坐标结果感到困惑时：浏览器截图 → 多模态直接查看建筑外观，大差不差即通过
#   截图固定落在当前工作区 .playwright-mcp/page-<时间戳>.png，直接用返回的相对路径读图，无需搜索
#   build 同格覆盖：同一坐标后放覆盖先放（与 /setblock 一致）；返回值 overwritten>0 说明清单有坐标重叠，应回头检查
#   export 坐标归一化：导出坐标平移到三轴从 0 起，原始最小角在 origin_min 字段，属正常行为

# 第 3 步：交付（数据不过模型，蓝图无论大小一律走下载）
vd.download()   # blueprint.json 固定落在当前工作区 .playwright-mcp/blueprint.json（实测确认）
# 移动改名（路径固定，直接照抄，无需搜索）：
mv .playwright-mcp/blueprint.json <ENGINE>/schematics/<名字>.json
# 禁止用 vd.export() 返回值抄写 JSON；交付后不回读核对，设计阶段到此结束

# 第 3 步：根据 JSON 生成存档
node <skill>/scripts/write_litematic.mjs <ENGINE>/schematics/<名字>.json <ENGINE>/schematics/<名字>.litematic <名字>

# 第 1 至 2 步，路线 B：脚本设计
# 先将 design_template.mjs 复制到任意目录并改名，修改其中的 buildDesign 函数后运行：
node design_<名字>.mjs <原点x> <原点y> <原点z> <名字>
# 三件套会直接写入 <ENGINE>/schematics/，无需手动复制。
# 一次性设计脚本使用完毕后归档到工作区（例如 D:/work/minecraft/），不要堆积在技能目录中。
```

路线 B 的模板内置了模块导入约定（pathToFileURL 与 SKILL_SCRIPTS 常量），因此模板复制到任意目录均可正常运行。
