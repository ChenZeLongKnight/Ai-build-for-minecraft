# Minecraft 蓝图设计（设计阶段）

本技能负责 Minecraft 建筑流水线中的设计阶段，其职责是把设计构思或一张现成的图片转化为标准化的蓝图文件，产物写入引擎目录供后续流程取用。设计阶段不需要游戏世界处于运行状态，后续流程如何消费这些文件也不属于本技能的知识范围。

设计任务分两大类，动手前应先分清属于哪一类，再读对应的一节。**自主设计**由使用者提出构想，建筑、装置、地形均可，由 Agent 亲手把体素摆出来。**图片还原**的来源是一张现成的图片，要求按原样复现而非构思创作，不打开设计器，直接运行转换脚本产出蓝图。两类任务的蓝图格式与落地方式完全相同，区别只在于前半段如何得到体素清单。

## 通用约定

1. 引擎目录在下文中以 `<ENGINE>` 表示，其取值来自环境变量 `MC_BUILD_HOME`，默认值为 `D:/mcserver`。执行 Node 脚本时统一使用 `C:/Users/ASUS/.workbuddy/binaries/node/versions/22.22.2-2/node.exe`。
2. 两类任务产出的是同一套文件，统一以 `<名字>` 为前缀写入 `<ENGINE>/schematics/`：`<名字>.json` 是蓝图主文件（必需），内容为 `{width,height,length,blocks:[{x,y,z,block}]}`，坐标相对蓝图原点；`<名字>.litematic` 是存档文件（推荐），Litematica 模组可直接打开；`<名字>_fills.txt` 是 /fill 指令清单（按需生成），每行一条指令。
3. 深度参考资料位于本技能的 references 目录；本文件正文只描述流程与决策逻辑，全部可执行命令集中列于末尾的「命令速查」一节。

## 自主设计

由使用者提出构想、Agent 亲手摆放体素的路线。实现方式有两条：需要构思、试摆或查看效果的走设计器，这是主要方式；结构具有明显程序化特征（严格对称、循环重复单元、参数化曲线）而手工摆放不便的走脚本生成。除此之外不存在其他方式。

### 设计器

**禁止绕过设计器**：需要亲手摆放方块的任务必须通过设计器网页完成，不得凭空猜测坐标后手写体素清单——手写的坐标无法在设计阶段自查，错误只有到游戏中才会暴露，也不会有视觉反馈可供迭代。

**前置依赖与打开方式**：操控设计器必须使用 `mcp__browser-use` MCP 工具（以下称「浏览器工具」），后文所说的「打开页面」「调用 vd 接口」「截图」全部指通过该工具执行。页面地址为 `file:///<skill路径>/assets/voxel_designer.html#ai`，URL 末尾的 `#ai` 片段会让页面打开时自动运行全链自测以确认接口可用（改用 `#sample` 则自动载入水井示例）。页面依赖库位于同目录的 libs 文件夹，file 协议打开无任何网络依赖。

**调用方式**：通过浏览器工具的 JavaScript 求值功能直接调用页面的 `window.vd` 接口，不要模拟鼠标操作。所有方法同步返回 JSON，并镜像到页面右下角的 #aiOut 面板。

**接口全表**：

| 方法 | 说明 |
|---|---|
| `help()` | 输出接口总览 |
| `blocks(cat?)` | 输出全部 256 种可用方块 `[{id,label,mc,cat,shape}]`，按十二个分类组织（自然、石材、木材、混凝土、陶瓦、羊毛、玻璃、金属、铜制、装饰、植物）；可传分类名过滤（如 `blocks("混凝土")`） |
| `select(id)` | 选择默认方块，minecraft: 前缀亦可识别 |
| `place(x,y,z,id?)` / `erase(x,y,z)` | 单格放置与擦除 |
| `box(x1,y1,z1,x2,y2,z2, id\|null)` | 长方体填充；参数为 null 或 "air" 时清空该区域 |
| `build([[x,y,z,"stone_bricks"],…])` | 批量摆放，一次撤销批次加一次重建，是效率核心（上限 20 万格） |
| `voxels()` | 列出全部已放置的方块 |
| `state()` | 输出方块数、尺寸、各方块计数、工具、切片、相机与撤销深度 |
| `undo()` / `clear()` / `load(json)` | 撤销、清空与导入（接口层均不弹出确认框） |
| `export()` | 导出蓝图，返回 `{blueprint:{width,height,length,blocks:[{x,y,z,block}]}}` |
| `view('iso'\|'front'\|'back'\|'left'\|'right'\|'top'\|'fit')` | 相机预设 |
| `orbit(yawDeg,pitchDeg,dist?,tx?,ty?,tz?)` | 精确环绕相机 |
| `slice(true, y)` | 仅显示纵坐标不超过 y 的切片，用于检查内部结构 |
| `screenshot()` | 输出画布的 PNG dataURL（通常直接使用浏览器截图工具更方便） |
| `sample()` | 载入示例建筑水井 |

**两条容易误读的行为**：

- **build 的同格覆盖**：批量摆放时若多个条目落在同一坐标，后放的会覆盖先放的（与游戏内 /setblock 的覆盖写语义一致）。返回值中的 overwritten 字段报告本批次内被覆盖的次数，大于 0 通常意味着体素清单存在坐标重叠，应回头检查生成逻辑。
- **export 的坐标归一化**：导出时三轴各自平移到从 0 开始，原始最小角记录在返回值与蓝图的 origin_min 字段中。因此导出坐标与摆放时的输入坐标不一定相同，这不是错误；蓝图坐标本来就相对原点，落地定位由后续流程的 origin 参数负责，无需把 origin_min 加回蓝图。

**设计器的三条已知限制**：

- 放置方块不携带状态信息：半砖默认下半、楼梯默认朝北，栅栏与墙在游戏内自动连接故无影响。非整格方块在设计器中按真实比例渲染预览，导出的蓝图仍是方块名，由游戏应用默认状态。当设计需要定向楼梯、上半砖、悬挂灯笼等自定义状态时，应改走脚本路线，在模板副本中直接书写如 `minecraft:spruce_stairs[facing=south]` 的完整状态名；litematic 写入器与 /fill 指令都会原样携带状态，此路径已实测可用。
- 输出的树叶自动携带 `[persistent=true]` 状态（普通树叶附近无原木会自然凋零，这是设计器的内置修复）。
- 调色板即能力边界：build 接口会跳过调色板之外的方块并在返回值中报告 skippedUnknown，因此设计前应先用 blocks 接口核对可用方块（当前 256 种，覆盖 1.21 常用建筑方块）。若仍缺少所需方块，可向设计器的 BLOCKS 注册表补充（采用程序化像素纹理；技能资产与工作区副本两处文件均需修改）。

**物理规则（设计体素时必须遵守）**：

- 围水的墙体必须使用全方块（圆石、石砖等），墙、栅栏、台阶会漏水。
- 依附类方块必须有支撑：藤蔓依附于其属性所指一方的完整面，灯笼悬挂时上方须有方块、落地时下方须有方块，地毯、床、门必须贴地放置。
- 藤蔓不能依附于玻璃板，因为玻璃板不构成完整面；即使强制放置也会随方块更新被弹掉。若希望藤蔓攀爬玻璃窗，应将该格玻璃板换成玻璃块，或放弃该藤蔓。
- 悬空的沙子、混凝土粉末、沙砾会塌落，火把必须贴面放置。
- 依赖方块的支撑块必须先落地。落地工具按纵坐标自低向高执行，天然安全；同一层内的藤蔓类方块可能漏网，由后续流程验收后逐根补放。

**推荐的设计节奏**：清空画布，批量摆放主体，切换到适配视角配合截图检查整体，再以环绕相机与切片检查细节，修改后复查，核对数量与尺寸后交付。坐标系中 y=0 表示地面。

**视觉自查**：对坐标推算的结果感到困惑时，不要继续在数字层面反复推理，应立即调用浏览器截图能力，以多模态方式直接查看设计器中建筑的实际样子——看一眼渲染结果远比心算坐标可靠。截图固定落在当前工作区的 `.playwright-mcp/` 目录，文件名形如 `page-<时间戳>.png`，用工具返回的相对路径直接读图即可，不需要任何查找。判断标准是「大差不差」：只要形状、比例、朝向与设计意图大体相符即可通过，无需逐格核对坐标；发现明显偏差时，回到设计器修改后再次截图确认。本技能的截图通道（浏览器对设计器渲染画面）与 mc-screenshot 的 F2 截图通道（游戏内画面）是两条独立通路，互不通用。

**交付（数据不过模型，重要）**：设计完成即调用 `vd.download()`，由浏览器把蓝图落成磁盘文件，落盘位置固定为当前工作区的 `.playwright-mcp/blueprint.json`，直接移动改名为 `<ENGINE>/schematics/<名字>.json` 即可，不需要任何查找。无论蓝图大小一律走下载通道；禁止调用 `vd.export()` 后把返回值抄写或注入到模型上下文中再写文件——大蓝图会在上下文中进出一次，既浪费又可能抄写走样。文件落位后不再回读核对，正确性由后续流程的验收兜底；`vd.export()` 仅在需要查看方块数量等元信息时使用。`.litematic` 用 write_litematic.mjs 从 JSON 转换，`_fills.txt` 按纵坐标自低向高排序、同种方块的连续区段合并为一条指令。

### 脚本生成（对称 / 重复结构）

仅在结构具有明显程序化特征（严格对称、循环重复单元、参数化曲线）且手工摆放不便时使用。做法是复制 `design_template.mjs` 到任意目录并改名，修改其中的 `buildDesign` 函数后运行：

```bash
node design_<名字>.mjs <原点x> <原点y> <原点z> <名字>
```

三件套直接写入 `<ENGINE>/schematics/`。模板内置了模块导入约定（`pathToFileURL` 与 `SKILL_SCRIPTS` 常量），因此复制到任意目录均可正常运行。这条路不依赖浏览器工具。一次性脚本用毕归档到工作区，不要堆积在技能目录中。

## 图片还原

来源是一张现成的图片，要求按原样复现而非构思创作。这类任务不打开设计器，直接运行转换脚本产出蓝图，难点在于读懂图片而不在于设计造型。按源图类型选入口：

| 源图类型 | 脚本 |
|---|---|
| 照片（背景杂乱、画面里有无关物体） | `scripts/photo2blueprint.py`，自动识别并抠出画面主体，不需要人工裁剪或调整背景参数；画面里有多个可辨认的主体时，先列出候选再指定要哪一个 |
| 平涂像素图（拼豆、十字绣图纸） | `scripts/img2blueprint_flat.py` |
| 干净位图 / 光照均匀的照片 | `scripts/img2blueprint.py` |
| 建筑照片 | 先按 `references/photo-to-building.md` 判别类型，再走该文档的四条路线之一 |

脚本的使用细节、必须由人给出的参数、以及自动抠图不理想时的手工退路，见 `references/photo-to-pixelart.md`。

建筑照片不要拿到就开工。先按 `references/photo-to-building.md` 的四条路线分流（像素图 / 正交三视图 / 知名建筑查图纸 / 随手拍透视图），其中只有「剪影求交」是真正实用的三维路线，摄影测量路线的产出质量与工时不划算，应先向用户说明再决定。

交付由转换脚本直接写入 `<ENGINE>/schematics/`。

## 命令速查

```
# ── 自主设计 · 设计器 ──
file:///<skill路径>/assets/voxel_designer.html#ai
# 常用序列：vd.clear() 清空 → vd.build([...]) 批量摆放 → vd.view('fit') 检查整体
#           → vd.orbit(...) / vd.slice(true,y) 检查细节 → vd.state() 核对数量与尺寸
# 对坐标结果感到困惑时，直接用浏览器截图看渲染画面，大差不差即可
# 交付（数据不过模型，蓝图无论大小一律走下载）：
vd.download()   # blueprint.json 固定落在当前工作区 .playwright-mcp/blueprint.json
mv .playwright-mcp/blueprint.json <ENGINE>/schematics/<名字>.json
node <skill>/scripts/write_litematic.mjs <ENGINE>/schematics/<名字>.json <ENGINE>/schematics/<名字>.litematic <名字>

# ── 自主设计 · 脚本生成 ──
node design_<名字>.mjs <原点x> <原点y> <原点z> <名字>

# ── 图片还原 ──
python <SKILL>/scripts/photo2blueprint.py <照片> --width 160 --name <名字>
#   画面里有多个主体时先用 --list 看候选、再 --pick N 指定；照片偏暗致颜色发灰时加 --saturate 1.3。
python <SKILL>/scripts/img2blueprint_flat.py <图片> --width <原生格数> --name <名字>
python <SKILL>/scripts/img2blueprint.py <图片> --width 200 --bg auto --name <名字>
```
